## 第 1 轮：页结构与基本不变量

### Q1. `size_` 的两种含义

一个内部页有 `size_ = 3`。

1. 它有几个孩子指针？
2. 它有几个**有效**键？
3. `key_array_[0]` 里存的是什么？为什么要有这么一个「无效」的槽位？

**我的回答**

> 3 个子页指针 和 2 个被索引的键。这个键无效。

**纠错** `⚠️ 部分掌握`

1、2 两问完全正确：`size_` 数的是**孩子数**，所以 3 个孩子指针、`size_ - 1 = 2` 个有效键。

第 3 问答了结论（「这个键无效」），但没答**为什么要有这个槽位**。这是关键的一半。

真正的原因分两步：

**① 孩子 0 没有下界键。** 内部页的每个键是「某个孩子的下界」。孩子 i 覆盖 `[key[i], key[i+1])`，但孩子 0 覆盖 `(-∞, key[1])` —— 它左边没有边界，自然没有下界键可存。所以 n 个孩子只需要 n−1 个键。

**② 但两个数组必须等长、且下标对齐。** `page_id_array_[i]` 和 `key_array_[i]` 用同一个下标，好处是：

- `ValueIndex` 找到孩子下标 i 后，直接能用 `key_array_[i]` 和 `key_array_[i+1]` 界定它的范围，不用做 `i-1` 的换算
- 分裂/合并时两个数组可以在**同一个循环**里按下标同步搬移（`MoveHalfTo` 里就是 `page_id_array_[i] = ...` 和 `key_array_[i] = ...` 写在一起）

所以第 0 个槽位是「为了对齐而留的空位」，它的值是垃圾，**任何查找都必须从下标 1 开始**。这也是 `Lookup` 里 `lo = 1` 的来源。

一句话：不是「键比孩子少一个所以少存一个」，而是「为了下标对齐，多留了一个空槽」。

### Q1-a. 键是「区间」还是「边界值」？

追问：每个键是不是对应一个区间？记录的是一个边界值？

**我的回答**

> 追问形式：确认「键 = 区间」这个理解对不对。

**纠错** `⚠️ 需精确`

**存的是标量边界，不是区间。** 区间是**推导出来的**，不占存储。

内部页里存的是 n−1 个键，每个键是一个具体的 key 值（标量）。孩子 i 覆盖的范围由**相邻两个键夹出来**：

| 孩子 | 覆盖范围 | 下界来自 |
| --- | --- | --- |
| 0 | `(-∞, key[1])` | 无 |
| i（1 ≤ i ≤ n−2） | `[key[i], key[i+1])` | `key[i]` |
| n−1 | `[key[n−1], +∞)` | `key[n−1]` |

所以：

- 一个键只贡献**一个**边界
- 一个中间孩子需要**两个**边界，来自两条不同的记录
- 首尾两个孩子的另一侧是无穷，没有键对应

**左闭右开的原因**：`key[i]` 是孩子 i 子树里的**最小值**，所以它属于孩子 i，不属于孩子 i−1。而 `key[i+1]` 同理属于孩子 i+1。于是 `key[i]` 这个值本身一定走孩子 i。

**同一个值的两种看法**：

1. **边界**：它把 `key < 它` 和 `key ≥ 它` 分开
2. **子树最小值的副本**：它等于该孩子子树里的最小 key

第 2 种看法更本质——它给出了「父页里那条记录的 key 必须等于什么」这条不变量（第 4 轮会考）。

**为什么 n 个孩子只要 n−1 个边界**：一维空间被 n−1 个切点分成 n 段。孩子 0 和 n−1 各有一侧是无穷，不需要切点。

## 第 2 轮：查找路径

### Q2. `Lookup` 的边界

内部页的 `Lookup` 要找「最后一个满足 `key[i] ≤ 目标` 的下标 i」，`i` 的范围是 `[1, size_)`。

如果目标键**比所有键都小**，会返回哪个孩子？这个结果是怎么产生的——是二分找到了它，还是别的机制？

**我的回答**

> 返回 0。就是前面说覆盖 (-∞, key[1])

**纠错** `⚠️ 部分掌握`

「返回孩子 0」对，「孩子 0 覆盖 `(-∞, key[1])`」也对。但题目问的是**这个 0 是怎么来的**，答成了「因为它的范围是 (-∞, key[1])」——那是**语义上的解释**，不是**代码里的机制**。

二分**根本没有找到**孩子 0。它是「二分什么都没找到」时的兜底值：

```
child = 0            ← 初值
lo = 1, hi = size_ - 1
while (lo <= hi) {
  if (key[mid] <= 目标) { child = mid; lo = mid + 1; }   ← 只有这里会改写 child
  else                  { hi = mid - 1; }
}
return page_id_array_[child];
```

目标比所有键都小时，`key[mid] <= 目标` **一次都不成立**，`child` 从未被赋值，循环结束时它还是初值 0。

所以这是「初始化兜底」，不是「二分的结果」。

**为什么这个区别重要**（三个具体的坑）：

1. **`child` 必须显式初始化为 0。** 写成 `int child;` 不初始化，这个分支就返回栈上的垃圾值 —— 而且只在「目标比所有键都小」时触发，测试里很容易漏掉。
2. **初值不能随手写。** 写成 `size_ - 1` 会让「比所有键都小」的目标走最右孩子；写成 `-1` 会读 `page_id_array_[-1]`。
3. **二分区间从 1 开始，天生无法表达「0」这个答案。** 区间 `[1, size_)` 里没有 0，所以 0 只能来自区间之外 —— 也就是初值。

顺带一个推论：正因为有这个兜底，`Lookup` 的返回类型是 `page_id_t` 而不是 `std::optional`。它**永远有答案**，不像叶子页的 `Lookup` 会返回 −1。

## 第 3 轮：分裂的两种形态

### Q3. 中间键：复制还是上浮

叶子页分裂时，新页的最小键**复制**一份到父页，它仍然留在新页里。
内部页分裂时，中间键**搬**到父页，两边都不留。

1. 为什么必须不同？
2. 如果内部页也改成「复制一份、原页保留」，会在**删除**时引发什么具体问题？

**我的回答**

> 内部页也改成复制，会导致真实往下指的和逻辑存的不一样。

**纠错** `⚠️ 部分掌握`

第 1 问没答。第 2 问的方向摸到了「物理与逻辑不一致」，但没有落到**具体的失败模式**。下面拆成三层。

### 第 1 问：为什么必须不同

**叶子页是数据层。** 叶子页里的每个条目是 `key → RID` 的映射，key 本身就是数据。分裂只是把数据分成两堆，**一条都不能丢**。所以右半的 key 必须跟着 RID 留在右半页里；父页拿到的只是一份副本，作用是路标。

**内部页是路由层。** 内部页的 key 不指向任何 RID，唯一职责是划分区间。分裂时中间那个键正好是左右两半的分界点——它放在父页最合适，成了「去右半」的路标。它本来就不属于任何一侧，所以不需要留在子页。

一句话：**数据必须留在数据层，路标应该放在路由层。**

### 第 2 问：如果内部页也复制

**第一层：它和布局约定直接冲突。**

内部页的约定是「`key_array_[0]` 无效，查找从下标 1 开始」，且「n 个孩子配 n 个槽位」。要让中间键留在子页，只能让它占据 `key_array_[0]` —— 而那个槽位按约定**永远不会被读到**。

于是只剩两条路，都不好：

- 改约定，让 `Lookup` 从 0 开始 → 但最左孩子根本没有下界键，`key[0]` 对它无意义，约定还是不自洽
- 保留约定，把这个键存进 `key[0]` → 等于白存，还占了一个槽位，扇出变小、树变高

**第二层：删除时出现「同一棵树里两份相同的分隔键」。**

正常设计下，每个 key 只在一个叶子页里出现一次；内部页里的那份是**副本**，且必须始终等于子树最小值。

如果分裂时复制而不上浮，同一个值会在父页和子页各存一份。删除路径上需要**沿着路径向上更新每一层的分隔键**（因为子树最小值变了）。两份副本 → 更新一处漏一处 → 父页的路标说「≥ 50 去右边」，而左边某个内部页里还留着 50 的路标，指向一个已经不含 50 的子树。

查询 50 时走到左边，一路下去查不到。**而且树画出来看不出问题**——每个页内部仍然递增、叶子仍然有序，错的是跨页的对应关系。

**第三层：错误会累积。**

每分裂一次多一份冗余，每删除一次要同步所有副本。这类「多副本一致性」是最容易漏的，而且漏了不崩溃、只在特定 key 上表现。

### 面试里的一句话版本

> 叶子页的键是数据，分裂不能丢数据，所以复制；内部页的键是路标，分裂时它正好是分界线，所以上浮。如果内部页也复制，同一棵树里会有两份相同的分隔键，删除时更新子树最小值必须同步所有副本，漏一处就出现「树形看着对、某些 key 查不到」的静默错误。

### Q3-a. 叶子页里哪些是数据、哪些是路由？

追问：叶子页里到底哪些内容算数据层，哪些算路由层？

**我的回答**

> 追问形式：质疑「叶子页 = 数据层」这个说法太粗。

**纠错** `✅ 澄清`

**「数据层 / 路由层」是逻辑角色的划分，不是按页划分的。** 同一个页里可以两种都有。

叶子页的五个组成部分：

| 内容 | 角色 | 判据 |
| --- | --- | --- |
| `key_array_` + `rid_array_` | **数据** | 它们合起来才是 `key → RID` 的映射 |
| `next_page_id_` | **路由**（横向） | 不指向任何 RID，只决定「扫下一页走哪」 |
| `tombstones_` | 数据的**元信息** | 描述「某个条目是否还有效」 |
| `page_type_` / `size_` / `max_size_` | 元数据 | 描述这一页自己 |

所以严格说，叶子页里**也有路由设施**——`next_page_id_` 就是。它存在只是为了 Task 3 的迭代器能顺序扫，跟「数据在哪」无关。

**判断一个键是数据还是路标的唯一标准**：

> 把这个键丢掉，会不会丢失一条 `key → RID` 映射？

- 叶子页的 `key_array_[i]`：丢了 → `rid_array_[i]` 就失去意义 → **是数据**
- 内部页的 `key_array_[i]`：丢了 → 只影响「往哪走」，所有 RID 都还在 → **是路标**

这条判据直接推出 Q3 的结论：分裂时数据必须留在数据层，路标应该放在路由层。

**为什么 `next_page_id_` 不影响 Q3**：它不参与「某个键属于哪一页」的判定。分裂时它是**被维护的对象**（新页接在原页后面），不是**决定中间键去向的依据**。

### Q3-b. 叶子层是链表还是树？

追问：叶子层是不是一条顺序链表而不是树形？用途是给迭代器遍历？

**我的回答**

> 追问形式：确认「叶子层 = 链表」这个理解。

**纠错** `✅ 基本正确，需补三点`

对。**叶子层同时是两条结构：树的底层 + 一条单向链表。** 两者共存，服务不同的访问模式。

| 访问模式 | 走哪个结构 | 代价 |
| --- | --- | --- |
| 点查 / 插入 / 删除 | 树（从根往下） | O(log n) |
| 范围扫描 / 全表顺序扫 | 叶子链（从左往右） | 每页 O(1) 跳到下一页 |

**补充三点：**

**① 单向。** 只有 `next_page_id_`，没有 `prev_page_id_`。所以只能正向扫，`ORDER BY key DESC` 用不上这个索引（要反向扫就只能每页从根重新下来，或者建另一条反向链）。这是工程取舍，BusTub 只做单向。

**② 只有叶子层有链，内部页之间没有。** 内部页不需要顺序访问——它们的访问模式永远是「从根往下按 key 走」。

**③ 没有链也能做范围扫描，但代价不同。** 可以「找到起点叶子页 → 扫完 → 再从根下来找下一个叶子页」，每页 O(log n)。有了链是每页 O(1)。数据量大时差一个数量级。

**维护点（Task 3 才会暴露）**：

- **分裂**：`new->next = old->next; old->next = new;`
- **合并**：接收方继承被合并页的 `next`

这两处漏了，`GetValue` / `Insert` / `Remove` 全都正常，只有迭代器会漏数据——而且是在写 Task 3 时才发现的，届时很难联想到是分裂的问题。

**迭代器遍历的粒度**：迭代器在**条目**级前进（页内 `index++`），只有跨页时才用 `next_page_id_`。所以迭代器状态是「当前页 + 当前下标」，不是「当前页」。

### Q3-c. 验收：叶子页也上浮会怎样（迁移题）

**我的回答**

> 会丢数据吧，叶子层优先保存数据

**纠错** `⚠️ 结论对，推理没走完`

结论对，判据也用对了（「叶子层优先保存数据」= Q3-a 那条判据的反向使用）。但没给出要求的**具体场景**。走完一遍：

叶子页 `[10, 20, 30, 40]`，`max_size = 4`，插入 `50` → `size = 5 > 4` → 分裂，`mid = 2`。

**正常（复制）**

```
左 [10, 20]    右 [30, 40, 50]    父页新增 (30, 右页)
查 30 → 走右页 → 二分命中 → 返回 RID ✓
```

**错误（上浮）**

```
左 [10, 20]    右 [40, 50]        父页新增 (30, 右页)
查 30 → 30 >= 30 走右页 → 右页是 [40,50] → 二分找不到 → 返回 false ✗
```

`30` 从**叶子层彻底消失**了。它在父页里只是一个数字，不携带 RID。这条 `key → RID` 映射永久丢失——除非重新插入一次，否则任何查询、任何扫描都拿不回来。

而且**不报错、不崩溃**，只在查这一个 key 时返回 false。5000 个 key 里丢几个，很容易被当成「测试用例的问题」。

**层级判定**：第 2 层（判据）✅ 过；第 3 层（推失败模式）结论对但没走完；第 4 层（迁移）结论对。剩下第 5 层未测。

### Q3-e. 内部页为什么不能复制（追问链）

追问 1：内部页为什么不上浮不行？
追问 2：上浮的键是不是也当「子树最小 key」用？
追问 3：查 20 的时候，F' 怎么找到它？（追问 4：对应哪段代码）

**我的回答**

> 逐步确认：靠比 `key[1]` 小就直接走孩子 0；上浮键确实是新页子树的最小 key。

**纠错** `✅ 已掌握`

**① 一个具体例子**

`internal_max_size = 4`，内部页 F：

```
孩子：  [ P0   P1   P2   P3 ]
键：    [ --   10   20   30 ]
```

分裂（`mid = 2`）后：

```
原页 F ：孩子 [P0, P1]    键 [--, 10]
新页 F'：孩子 [P2, P3]    键 [--, 30]
父页新增：(20, F')
```

`20` 不在 F 里，也不在 F' 里，只在父页。

**② 为什么 F' 不需要存 20**

因为 `20` 是「到达 F' 的 key 的下界」，而这件事**父页已经保证了**：`Lookup` 在父页用 20 判断 `< 20` 走 F、`≥ 20` 走 F'。所以能到 F' 的 key 一定 `≥ 20`。F' 内部只需区分 P2 / P3，用 30 就够。

**③ 叶子页为什么相反**

叶子页 `L' = [30, 40, 50]`，父页只存了 **30**。40 和 50 只存在于 L' 里。如果 30 也不留在 L'，30 就彻底消失了——父页那个 30 不带 RID。

| | 父页存了什么 | 中间键能不能丢 |
| --- | --- | --- |
| 叶子页 | 只存这一页的**第一个** key | 不能，其余 key 没有第二份 |
| 内部页 | 存这一页的**下界** | 可以，下界本来就在父页，且子页用不到 |

**结论：不是两种风格，而是「这个键的正本在哪」决定的。**

**④ 查 20 的完整路径（`size_ = 2` 的 F'）**

```
父页 Lookup(20)：cmp(key[1]=20, 20) = 0 → child = 1 → 走 F'
F'  Lookup(20)：lo=1, hi=1, mid=1
                cmp(key[1]=30, 20) = +1 → 不 <= 0 → hi = 0，循环结束
                child 从未改写，仍是初值 0 → 走 P2
到 P2 子树继续往下，直到叶子页二分命中
```

F' **全程没用到 20**，它只知道「比 30 小走 P2」。这就是上浮成立的证明。

**⑤ 对应代码**（`b_plus_tree_internal_page.cpp:72-88`）

| 行 | 作用 |
| --- | --- |
| `int child = 0;` | 「比 `key[1]` 小」这个分支的唯一来源（二分区间里没有 0） |
| `int lo = 1;` | 跳过无效的 `key_array_[0]` |
| `cmp(key_array_[mid], key) <= 0` | 用 `<=` 而非 `<`：相等时走**右边**孩子（左闭右开） |
| `return page_id_array_[child];` | 返回孩子 page_id，不是下标 |

`<=` 写成 `<` 的后果：目标 = 30 时会走 P2 而不是 P3，查不到。

## 第 4 轮：删除与下溢

### Q4. 借位还是合并

一个叶子页删到只剩 1 个条目（`max_size = 4`，所以 `min_size = 2`），需要修复下溢。

1. 兄弟页可能有几种状态？每种状态该做什么？
2. 如果无脑「总是合并、从不借位」，会在哪种状态下出问题？具体坏在哪？

**我的回答**

> 就是优先借 > 合并。如果兄弟有富余就借。两个都没富余合起来是满或者接近满吧。如果稍微大点，就会大于 max_size 上溢。

**纠错** `⚠️ 部分掌握`

主干全对：**优先借位、兄弟有富余才借、兄弟太大时合并会溢出**。

一处数字偏差：「两个都没富余合起来是满或接近满」——实际是 **3，离满（4）还差一条**。

`max_size = 4`、`min = 2`、`cur = 1`（下溢后）时，三种情况的精确账：

| 兄弟 `size` | 合并后 | `≤ max_size`? | 该做什么 |
| --- | --- | --- | --- |
| 2（`== min`） | 1 + 2 = **3** | ✅ | **只能合并**（兄弟没富余，借了它下溢） |
| 3（`> min`） | 1 + 3 = **4** | ✅ 刚好 | **借**（优先）；合并也合法但会级联 |
| 4（满） | 1 + 4 = **5** | ❌ | **必须借** |

所以：

- 「必须合并」的唯一情形：`sib == min_size`（2）
- 「必须借位」的唯一情形：`sib == max_size`（4）
- `sib == 3` 两种都合法，按「优先借」选借——因为借位不级联

**为什么两个 min 页合并后是 3 而不是 4**：合并的是「一页剩 1 条」和「一页有 2 条」，加起来 3。要达到 4 需要 cur 剩 2 条，但那时它就没下溢了。

**一般化的安全性**：`min = ceil(max/2)` 时，两页都是 min 的话 `2*min - 1 ≤ max` 恒成立（`max=4` → `3 ≤ 4`；`max=5` → `5 ≤ 5`）。所以「兄弟刚好半满时合并」永远装得下。

**代码里的对应**（`b_plus_tree.cpp` 的 `FixUnderflow`）：

```cpp
if (sib_leaf->GetSize() > sib_leaf->GetMinSize()) {   // 有富余 → 借
  ...
}
if (cur_leaf->GetSize() + sib_leaf->GetSize() > cur_leaf->GetMaxSize()) {
  return;                                             // 合并会溢出 → 放弃
}
// 否则合并
```

第二个 `if` 就是兜住 `sib == 4` 那种情况——只在「借位没解决问题」（墓碑被应用导致 cur 仍然欠满）时才会走到。

**判定：`⚠️ 部分掌握`** —— 策略对，具体容量账算错了一处。这类数字在调试时很重要：`cur + sib > max` 这个判断写错，表现就是某一页悄悄变成 5 条，`b_plus_tree_printer` 能看出来但测试不报错。

## 第 5 轮：树高与根的特殊地位

### Q5. 树什么时候变矮

删除会让树变矮。

1. 什么条件下树会变矮一层？涉及哪两种页的什么状态？
2. 「允许只剩 1 个孩子」这个豁免为什么只给根？如果某个**非根**内部页也只剩 1 个孩子，会发生什么？

**我的回答**

> （要求先讲解，尚未作答）

**讲解**

**① 树高怎么定义**

树高 = 从根到叶子经过的**页数**。

| 状态 | 树高 |
| --- | --- |
| 空树（根无效） | 0 |
| 只有一个叶子页 | 1（根就是叶子） |
| 根是内部页 + 叶子层 | 2 |

**② 变矮只有一种触发条件**

> **根是内部页，且它只剩 1 个孩子。**

这时根没有任何「分叉」作用，只是个把父页指针转发给唯一孩子的中转页。删掉它，让那个孩子当新根，树高 −1。

发生路径：删除 → 叶子页下溢 → 借位/合并 → 父页少一个孩子 → 如果父页是根且只剩 1 个 → 降级。**树变矮是删除级联的终点。**

**③ 为什么豁免只给根**

因为**根没有父页，也没有兄弟**。

- 非根页下溢 → 有邻居 → 可以借位或合并
- 根下溢 → 没有邻居 → 借不了、合不了 → 唯一出路是收缩

所以「只剩 1 个孩子」对根不是违规，而是「它能做到的极限」。

**④ 非根内部页只剩 1 个孩子会怎样**

那叫**下溢**，必须继续修复。`min_size = ceil(max_size/2)`，`max_size = 3` 时 `min = 2`，1 个孩子 < 2，违规。

不修复的后果：这类「单孩子中转页」会累积，每层都可能出现，最后整棵树退化成一条链，查找变成 O(n) 次页读取，而且每层白读一页。

**⑤ 其实有「两种」根退化**

| 情况 | 处理 | 结果 |
| --- | --- | --- |
| 根是**内部页**，只剩 1 个孩子 | 根降级为那个孩子 | 树高 −1 |
| 根是**叶子页**，被删空（`size == 0`） | 根置为 `INVALID_PAGE_ID` | 树空了 |

第二种不是「变矮」，是「树消失」。叶子根的 `min_size ≥ 1`，所以 `size == 0` 也是下溢——但它没有兄弟，只能变成空树。

**⑥ 对称的一点：树什么时候长高**

只有**根分裂**时。中间层的分裂/合并只改变**宽度**，不改变高度。

所以「树高变化」永远只发生在根上：**长高靠根分裂，变矮靠根收缩。**

**⑦ 代码对应**（`b_plus_tree.cpp` 的 `Remove`）

| 位置 | 条件 | 动作 |
| --- | --- | --- |
| 循环内 `if (path.empty())` | parent 是根且 `GetSize() == 1` | `header->root_page_id_ = parent->ValueAt(0)` |
| 循环外，根是叶子 | `root_leaf->GetSize() == 0` | `header->root_page_id_ = INVALID_PAGE_ID` |
| 循环外，根是内部页 | `root_internal->GetSize() == 1` | `header->root_page_id_ = root_internal->ValueAt(0)` |

**我的回答**

> 树根子节点只有一个。非根剩一个算下溢。

**纠错** `⚠️ 部分掌握`

两个结论都对：

- 根只剩 1 个孩子 → 树变矮 ✓
- 非根剩 1 个孩子 → 下溢 ✓

但第 2 问的**「为什么」没答**。结论可以背，机制不能。

**为什么豁免只给根——因为它没有邻居。**

下溢的修复手段只有两个，都依赖「有兄弟」：

- 借位：从兄弟挪一个过来
- 合并：和兄弟合成一页

根**没有父页，也没有兄弟**。它只剩 1 个孩子时，借不了、合不了，唯一出路是把自己删掉、让孩子顶上来。

所以这不是「根被特殊优待」，而是「根是唯一一个没有邻居的页，所以它的下溢只能靠收缩解决」。**豁免的本质是「没有兄弟」，不是「它是根」。**

**非根内部页剩 1 个孩子为什么必须修**：`min_size = ceil(max_size/2)`，`max_size = 3` 时 `min = 2`。1 < 2 违规，而且它有邻居——有邻居却不管，就是漏修。漏修的后果是「单孩子中转页」在每一层累积，每层白读一页，树退化成链。

**还漏了第二种根退化**：根是**叶子页**且被删空（`size == 0`）→ 根置为 `INVALID_PAGE_ID`，树变成空。这不是「变矮」，是「树消失」，但它同样是「根没有兄弟」这条规则的推论。

**一句话对照**：

| 页 | 剩 1 个孩子 | 理由 |
| --- | --- | --- |
| 根（内部页） | 合法，收缩 | 没有兄弟，无处可借可合 |
| 非根（内部页） | 下溢，必须修复 | 有兄弟，能借能合 |
| 根（叶子页，0 条） | 树变空 | 没有兄弟 |

**判定：`⚠️ 部分掌握`** —— 结论对，机制缺失。面试里这题就是在考「你能不能说出为什么」，光答结论会被追问到卡住。

## 第 6 轮：墓碑（懒删除）

### Q6. 为什么删除不直接删

你的实现里，`NumTombs > 0` 时删除一个 key **不会**真的把条目从 `key_array_` 里拿走，而是在 `tombstones_` 里记一个下标。

1. 这样做省下了什么开销？
2. 代价是什么？至少说出**两个**必须额外处理的点。
3. 如果这个 key 之后被**重新插入**，你的代码怎么处理？

**我的回答**

> 省去了频繁 O(n) 删除，代价是有时候必须删除，和多出的空间复杂度。如果重新插入就直接按插入逻辑来，并把墓碑设 0。

**纠错** `⚠️ 部分掌握`

**第 1 问 ✓**：省掉的是「物理删除时的数组搬移」——删第 i 条要把 `[i+1, size)` 整体左移一格，一页 254 条时平均搬 127 次，每次拷 16 字节。墓碑把它降成 O(1) 的追加。

**第 2 问 方向对但太浅**：「有时候必须删除」= 缓冲区满时要应用最老的，对；「多出的空间复杂度」也对。但真正麻烦的代价是**一致性维护**，至少四条：

| 代价 | 具体 |
| --- | --- |
| 读路径处处要跳 | `GetValue` 命中后要查墓碑；迭代器 `operator++` 要跳过；`Insert` 的唯一键判断要区分「命中且未墓碑」 |
| **下标会失效** | 插入/物理删除会让元素移位，所有受影响的墓碑下标都要重算（`InsertAt` 里 +1、`RemoveAt` 里 −1） |
| 分裂/合并/借位要搬 | `MoveHalfTo` 按下标分流并减 `mid`；`MoveAllTo` 追加在后面；还要防容量溢出（`MakeTombstoneRoom`） |
| 逻辑大小 ≠ 物理大小 | `size_` 含作废条目，所以「满不满」「够不够半满」的判断和 `NumTombs == 0` 时含义不同 |

**第 3 问 ✗ 逻辑错了。**

「按插入逻辑来」会在页里造出**两条 key 相同的物理条目**——一条带墓碑、一条不带。而 `Lookup` 返回的是**第一个**相等的下标，正好是那条带墓碑的 → `GetValue` 返回 false，可新数据就在旁边。

**正确做法：复用那个作废的槽位。**

```cpp
int index = leaf->LowerBound(key, comparator_);
if (index < leaf->GetSize() && comparator_(leaf->KeyAt(index), key) == 0) {
  if (!leaf->IsTombstoned(index)) {
    return InsertResult::kDuplicate;      // 真的已存在
  }
  leaf->SetValueAt(index, value);         // 原地改 RID
  leaf->RemoveTombstone(index);           // 撤掉那条墓碑
  return InsertResult::kInserted;         // size_ 不变
}
```

三件事：**改 RID、撤墓碑、`size_` 不变**。不是插入，是「复活」。

**另外「把墓碑设 0」这个说法也不对。** 墓碑数组里存的是**下标**，`0` 是一个合法的下标——设成 0 等于「标记第 0 条作废」，语义完全反了。正确动作是**把那条墓碑记录从数组里移除并把后面的压实**（`RemoveTombstone` 做的就是这个）。

**判定：`⚠️ 部分掌握`** —— 第 1 问对，第 2 问太浅，第 3 问有实质性错误。第 3 问是这题的关键：它同时考「你懂不懂墓碑的语义」和「你知不知道自己的代码怎么处理的」。
